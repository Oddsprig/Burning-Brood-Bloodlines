### Ranked findings — highest player impact first

#### H01 — Offered longer histories conflict with mandatory ruler design

**Status: confirmed source defect. Confidence: high; history-day implementation independently supplied by the controller, runtime unrun.** Trigger: choose a history of two or more days, then reach “Design your ruler.” The history picker offers 1–30 individual days and years (`game/ui/newgame.gd:161`). `CharacterDesign.preview` rejects `game.day > 1` (`game/campaign/character_design.gd:151`); `apply` repeats the gate at line 237. The mandatory stage disables Next on that rejection (`game/ui/house_select.gd:387`) and `next_stage` requires a valid design at line 487, with no skip.

The controller supplied the missing `game/campaign/world_presim.gd:286`, `:306` and `:323` dependency: history advances `game.day`, and finish does not reset it. In the supplied code, `game/ui/presim.gd:270` finishes history → prepares dynasty → `Game.new_game_finalize` → HouseSelect; `game/core/game.gd:232` does not reset the day either. Thus the exposed longer-history route cannot complete its required source gates. The default one-day route is unaffected. No failed engine run is inferred.

**Smallest useful v0.095 scope:** make initial ruler design depend on the actual initial-selection boundary rather than absolute world day, while retaining stable leader validation and one-time focus application. Keep the chosen history/day, existing people, purse and RNG. Do not bypass the issue by resetting history or removing the offered history choices.

#### H02 — A betrothal can complete while the other partner is still a child

**Status: confirmed source defect. Confidence: high for the age contradiction; exact downstream register effects require the missing person implementation.** Trigger: betroth a member to a younger candidate, then advance until only the member is adult. `Marriage.candidates` includes child candidates down to adult age minus six (`game/campaign/marriage.gd:119`, `:141`); `propose` stores the betrothal (`:229`). `daily` checks only party `a` (`:337`) before `wed`; `wed` validates existence at `:245` but no adulthood for either partner before moving dowry/person/egg and writing spouse/alliance/claim fields (`:254`, `:259`, `:281`, `:297`). The source therefore permits an early wedding. Its adult-only `pp` removal/counter path also makes child-register handling a concern, not a proven duplicate-person result without `Persons.forget`/aging source.

**Smallest useful v0.095 scope:** require both partners to be eligible adults before betrothal completion and revalidate the same pair immediately before any payment or transfer. Retain the betrothal while one is underage. Preserve native kin, custody, wage and household transitions; no new marriage system is needed.

#### H03 — Politics browsing can become a saved relocation

**Status: confirmed source defect. Confidence: high for saved location and map repositioning; Town-screen internals are outside this snapshot.** Trigger: from a party away from its home, open House → Politics, browse another settlement, then save or quit without using the Politics Back button. `PoliticsView.open_view` writes the viewed town to `Game.location` (`game/ui/politics.gd:17`), and `_select` does so again at `:288`; only `_back` restores the old value (`:340`). These changes do not move the party at browsing time.

The save chain is concrete: pause Save/Title/Quit can save Politics (`game/core/mobile_app.gd:54`, `:63`, `:303`, `:372`); `SaveSnapshot.begin` copies that viewed location (`game/core/save_snapshot.gd:20`); `Game.load_game` restores it (`game/core/game.gd:1165`); Title Continue opens Town when it is nonempty (`game/ui/title.gd:74`). When Map is entered with a nonempty location, `_ready` explicitly places `world.party.pos` at that town's gate and clears the field (`game/campaign/world_map.gd:84`). This is a reload-origin relocation path, not merely an incorrect label while browsing. The intermediate Town behavior still needs root inspection.

**Smallest useful v0.095 scope:** keep viewed settlement/return context in screen parameters and preserve physical `Game.location` while browsing; review Population/Records return paths before integration. Retain actual town-arrival behavior.

#### H04 — Save success is announced before the writer succeeds

**Status: confirmed source defect. Confidence: high; no disk failure was induced.** Trigger: press Map Save when a write is deferred or fails. `_on_save` requests an asynchronous save and immediately toasts “Game saved.” (`game/campaign/world_map.gd:719`). A real world can merely set `_save_pending` first (`game/core/game.gd:568`); open/write/rename failures return receipts (`:1078`) accepted later at `:623`. The indicator only shows capture activity (`game/ui/save_indicator.gd:22`), not a failed write. `MobileApp.autosave` returns true after calling a void save method (`game/core/mobile_app.gd:63`), and `confirm_quit` exits after waiting without checking the receipt (`:372`). The existing writer preserves the prior complete save on failure, but UI can promise that newer progress was saved when it was not.

**Smallest useful v0.095 scope:** connect queued/capturing/writing/success/failure feedback to the accepted save receipt; report success only on completion and make failed quit-save visible before discarding the current session. Preserve the codec, atomic writer and battle-save exclusion.

#### H05 — House improvements accept incomplete material supply and expose effects before build completion

**Status: confirmed source defect. Confidence: high in the owning functions; natural frequency/runtime consequences unmeasured.** Trigger: an affordable house has only one of an improvement's required goods, with the others absent, and the AI purchase path selects it. `improvement_preview` permits `shortfalls` whenever *any* required material is stocked (`game/campaign/house_upkeep.gd:717`, `:732`). `start_improvement` takes only `min(need, have)` (`:806`), pays the quoted material bill, then records the full next `level`, `weeks_left` and effects (`:833`). `_imp_level` and `_refresh_effects` read that new level without excluding unfinished work (`:512`, `:548`); the timer is decremented separately at `:910`. Full material delivery and elapsed construction are therefore not prerequisites to the recorded level/effect calculation.

This backend is not merely hypothetical UI: `weekly` calls `_maybe_ai_purchase` (`:967`), which calls `_ai_try_buy_improvement` → `start_improvement` (`:1007`, `:1045`). The controller supplied the external `Families.turn` call at `game/campaign/families.gd:1128`; that file was not read here.

**Smallest useful v0.095 scope:** enforce actual complete material custody or explicitly retained unfinished requirements, and distinguish active level/effects from building level until completion. Coordinate this economic boundary with the economy owner before exposing more improvement controls.

#### H06 — Automatic house spending has no corresponding management controls

**Status: UI unreachable for the supplied house/court screens. Confidence: high for these screens and automatic player spending; other unsupplied Records panels need root verification.** House exposes accounts/funding but no staff, improvement, event-budget or automatic-spending management (`game/ui/house.gd:94`, `:119`); Court adds family/marriage, grants, plots and prisoners (`game/ui/court.gd:82`). Existing `HouseUpkeep.set_staff_tier`, `summary`, `start_improvement` and the non-treasure `CourtEvents.preview`/`hold` branches have no callers in the supplied UI (`game/campaign/house_upkeep.gd:784`, `:871`, `:1152`; `game/campaign/court_events.gd:123`).

The controller supplied `game/campaign/families.gd:1130` calling `CourtEvents.weekly`. Its player-house branch only updates victory markers (`game/campaign/court_events.gd:343`), then falls through to reserve-driven hoard sales and shared automatic treasure/events/gifts spending (`:350`, `:368`, `:373`). The player can manually buy/sell treasure, but cannot inspect or direct these other decisions through the supplied House/Court controls.

**Smallest useful v0.095 scope:** an actual household cost/automatic-spending readout and a bounded choice over existing spending, after H05 and the complete external UI call graph are reviewed. Do not replace working treasure controls or assume a new grand-court simulation is required.

#### H07 — Marriage buttons commit money and asset terms not fully shown beforehand

**Status: confirmed source defect in the proposal presentation/transaction contract. Confidence: high.** Trigger: press “With a modest/generous gift,” or accept a dragon-house match. The card shows a no-gift verdict, limited reasons and optional egg name, then calls `Marriage.propose` directly (`game/ui/court.gd:451`, `:461`, `:464`). It shows neither the numerical gift nor the dowry/residence/claim terms in a final review. `_offer` calculates 2%/6% of the current payer purse, gift-dependent acceptance and 3% dowry (`game/campaign/marriage.gd:184`); `propose` immediately transfers the gift (`:222`). There is also a concrete quote mismatch: `_offer` advertises an egg only at score ≥ ACCEPT+10 (`:190`), but `wed` transfers the first eligible egg without that score condition (`:284`).

**Smallest useful v0.095 scope:** a reviewed, current pair-and-assets quote before commitment, including exact gift, dowry, residence, dynasty/claim/alliance consequences and the actual egg transfer. Match execution to those terms and revalidate eligibility before charging. The original handoff's terms presentation is proposed scope, cited below, rather than a new authorization.

#### H08 — Bounded Court lists hide actionable records without paging

**Status: UI unreachable beyond the displayed slices. Confidence: high for the limits, occurrence unmeasured.** Trigger: a realm holds more than 40 of the player's people, or a member has more than 12 returned spouse candidates. Court lists only the first 40 captives/held prisoners and displays “and N more,” with no next-page or search (`game/ui/court.gd:258`, `:323`, `:335`). Enemy-held overflow has no bulk “Pay all”; AI offers may expose some people but do not provide individual selection of all overflow. The backend returns up to 24 marriage candidates (`game/campaign/marriage.gd:149`), while Court displays only 12 (`game/ui/court.gd:442`). Held-prisoner “Ransom all”/“Release all” do work across the held list (`:371`) and are not missing.

**Smallest useful v0.095 scope:** preserve bounded row construction while adding stable-ID paging/search and explicit counts for both lists; retain the current payment/review gates.

#### H09 — A council/spymaster is a design gap, not the current Court's absence

**Status: missing design. Confidence: high for supplied owners/screens, no claim about unseen source classes.** Trigger: the player wants to appoint a court adviser or replace a dead regent. Offices and regency do exist: `Dynasty.appoint` records an adult regent for a minor (`game/campaign/dynasty.gd:853`), and Laws displays it (`game/ui/house_laws.gd:139`). There is no adviser appointment/control in Court's panel construction (`game/ui/court.gd:82`). Intrigue's “spymaster” is narration; defense uses the company's best judge/negotiator skill rather than a named council post (`game/campaign/intrigue.gd:36`, `:178`, `:260`). Office succession skips a still-living ruler (`game/campaign/dynasty.gd:934`), so the supplied code does not replace a dead regent while that ruler survives; Laws instead filters the dead regent (`game/ui/house_laws.gd:26`).

**Smallest useful v0.095 scope if separately designed/authorized:** one real adviser or regent-replacement rule tied to native identities, explicit authority and existing effects. The original handoff calls a small useful court/council proposed scope (`docs/handoff/original/HANDOFF_BURNING_BROOD.txt:100`, `:138`); it does not authorize invented roles or bonuses. This ranks below the confirmed entry/state defects.

#### H10 — Negotiated peace/war demands remain deferred design

**Status: missing design. Confidence: high for the supplied diplomacy API/UI.** Trigger: a player wants to specify treaty demands after a war. Relations' actual actions are alliance, pact and break (`game/ui/relations.gd:105`, `game/campaign/diplomacy.gd:410`); faction war/peace and 60–120-day truces already run through native diplomacy (`game/campaign/diplomacy.gd:546`, `:698`). Marriage/fabricated claims already exist (`game/campaign/marriage.gd:311`, `:363`, `game/campaign/intrigue.gd:203`), and conquered towns can be granted/revoked. No demand-selection/negotiated settlement action is exposed here. Treaty proposal authority is currently derived from the selected house's realm, without a sovereign gate (`game/campaign/diplomacy.gd:348`, `:404`); what authority an ordinary house should possess needs a design decision, not an assumed defect.

**Smallest useful v0.095 scope if separately designed/authorized:** define one bounded settlement demand and who may negotiate it, using existing claims, ownership, costs and truces. `docs/specs/diplomacy.md:44` explicitly defers envoys/brokered peace; the original Brood handoff proposes war demands and bounded goals (`docs/handoff/original/HANDOFF_BURNING_BROOD.txt:103`, `:159`). Neither prior assistant suggestions nor the working v0.092 guard justify inventing a new war system in this audit.
